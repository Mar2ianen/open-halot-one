# CL-60 WebSocket control protocol

This page documents the vendor WebSocket service used by `PrinterUI`, separately from the Linux-to-STM32 UART protocol in [protocols.md](protocols.md). Findings come from the ARM library copied from this printer and static call-path analysis. No status, pause, stop, upload, or print command was sent to the live service as part of this analysis.

## Listener and transport

The running `PrinterUI` process has a listener on TCP port `18188`. The latest runtime listing showed `:::18188` (IPv6 wildcard); IPv4 dual-stack behavior was not tested. The local listener address is omitted here.

The private copy of `/usr/lib/libcxWebsocket.so` is an ARM ELF32 shared library, 173,404 bytes, SHA-256 `47cd9804209c56a704e151f8a2c76db0957e1dca83200d15b3f463cf319e8a23`. The library is not redistributed in this repository.

Despite the class name `CxSslEchoServer`, its constructor at `0x1374c` constructs `QWebSocketServer` with `SslMode` value `1`. The target Qt 5 API assigns `1` to `NonSecureMode` (`ws://`) and `0` to `SecureMode` (`wss://`); the constructor separately creates an SSL configuration, but Qt documents that SSL configuration has no effect in non-secure mode. This is therefore a plain WebSocket service, not TLS. See the [Qt 5 QWebSocketServer reference](https://doc.qt.io/qt-5/qwebsocketserver.html).

`processTextMessage(QString)` at `0x144c4` converts the text to UTF-8 and `messageToJson(QString)` at `0x151a0` accepts only a JSON object. The server matches the sending socket to its `CxWebHandle` and dispatches the object to that connection's handler. Binary WebSocket messages go through a separate callback into `CxFileTransHandle::processBinary(QByteArray)`.

## Text command vocabulary

`CxFileTransHandle::processJson(QJsonObject)` at `0x19b8c` reads the top-level string key `cmd` and compares it to the `TRANSCMD` Qt enum names. The enum values and names recovered from the library are:

| Value | `cmd` | Handler / current finding |
|---:|---|---|
| 0 | `TRANSCMD_NULL` | Null/default enum value |
| 1 | `START_FILE` | Enters `startFile(QJsonObject)` |
| 2 | `CANCEL_FILE` | Enters `cancelFile(QJsonObject)` |
| 3 | `START_DATA` | Not dispatched as a JSON request; emitted as the per-binary-message upload acknowledgement |
| 4 | `CHECK_DATA` | Not dispatched as a JSON request; emitted when the uploaded file reaches its declared size |
| 5 | `START_PRINT` | Enters `startPrint(QJsonObject)` |
| 6 | `PRINT_PAUSE` | Enters `printPause(QJsonObject)` |
| 7 | `PRINT_STOP` | Enters `printStop(QJsonObject)` |
| 8 | `GET_PRINT_STATUS` | Enters `getPrintStatus(QJsonObject)` |
| 9 | `VERSION_CHECK` | Enters `verSionCheck(QJsonObject)` |
| 10 | `PRINT_PARA_SET` | Enters `setPrintPara(QJsonObject)` |

The listed command words are binary-confirmed CL-60 network commands, not STM32 UART commands. `processJson(QJsonObject)` dispatches the text commands listed above, but has no `START_DATA` or `CHECK_DATA` JSON branch. Those enum values are generated by the binary upload handler instead.

The library's JSON field strings include `cmd`, `filename`, `size`, `offset`, `token`, `errorcode`, `compress`, `received`, and `checkstate`. The status reply path additionally uses `status`, `printStatus`, `sliceLayerCount`, `curSliceLayer`, `printRemainTime`, `initExposure`, `delayLight`, `printExposure`, `printHeight`, `eleSpeed`, `bottomExposureNum`, `layerThickness`, and `resin`. The field inventory is recovered; not every field's role in every command has been traced.

## Status request, authentication, and reply

`GET_PRINT_STATUS` reads a top-level `token` string and passes it to `CxSslEchoServer::getPrinterStatus`, which emits `sigGetPrinterStatus(PrintStatusPara&, QString)`. `PrinterUI`'s slot calls `WebsocketTransFile::checkToken(QString)`. That function compares the supplied string with `Cencrypt::getEncryptData()`; `Cencrypt::init()` loads the source text from the printer's local configuration and stores an encrypted form, which `getEncryptData()` returns. The configured value itself is not included in this document.

The `Cencrypt::doEncrypt(QString)` path converts the input to UTF-8, calls `des_encrypt_str`, applies DES to 8-byte blocks with PKCS#5/PKCS#7-style padding, and Base64-encodes the ciphertext. The custom block routine has no chaining or IV state, so it is equivalent to DES-ECB. The embedded key bytes and the input/padding/Base64 recipe match Creality-Control's public `_generate_token()` implementation. A client can therefore reproduce the static token algorithm when it has the same configured source text. Separately, a read-only live status request using the printer's configured token was accepted, as described below; this confirms the device's auth path but does not independently test a freshly generated client token. A rejected token sets the print-state result to `TOKEN_ERROR` (state value 8).

For a valid status request, `getPrintStatus(QJsonObject)` builds and sends a JSON text object with `cmd: "GET_PRINT_STATUS"`, a string-valued `printStatus`, and these string-valued fields copied from `PrintStatusPara`:

```json
{
  "cmd": "GET_PRINT_STATUS",
  "printStatus": "PRINT_PROCESSING",
  "filename": "…",
  "sliceLayerCount": "…",
  "curSliceLayer": "…",
  "printRemainTime": "…",
  "initExposure": "…",
  "delayLight": "…",
  "printExposure": "…",
  "printHeight": "…",
  "eleSpeed": "…",
  "bottomExposureNum": "…",
  "layerThickness": "…",
  "resin": "…"
}
```

The code constructs JSON strings for these fields; clients should not assume that their wire types are JSON numbers. The state labels returned by `getPrintStatusKey(int)` are:

| Value | State label |
|---:|---|
| 0 | `PRINT_GENERAL` |
| 1 | `PRINT_PROCESSING` |
| 2 | `PRINT_COMPLETE` |
| 3 | `PRINT_FAIL` |
| 4 | `PRINT_END` |
| 5 | `PRINT_STOP` |
| 6 | `PRINT_STOPING` |
| 7 | `PRINT_COMPLETING` |
| 8 | `TOKEN_ERROR` |

The recovered status reply builder includes `filename` but not `progress`. It also includes the current layer, total layer count, and remaining time. A read-only `GET_PRINT_STATUS` request to the live printer on 2026-09-29, using its locally configured token, was accepted; the response contained the fields listed above, and every value was a JSON string. The live response also omitted `progress`. No status values or token were retained in the public documentation.

## Start, pause, stop, and parameter handlers (static only)

The following behavior comes from the saved ARM ELF and the matching `PrinterUI` binary; these requests were not sent to the live WebSocket service. The token/state checks, Qt state transitions, worker status changes, and static routes to UART helpers are mapped. The physical motor/output effect is not proven.

`startPrint(QJsonObject)` parses `filename` and `token`, but only the filename is used in this handler. It first calls `getFilePrintStatus(filename, true)`. For a nonzero result it sends `{cmd:"START_PRINT", status:..., filename:...}`; result `6` maps to `PRINT_STOP`, and other nonzero results map to `PRINT_PROCESSING`, then the handler returns false. When that check is zero but the handler's internal state at `this+0x4c` is `2`, it replies `PRINT_COMPLETE` using the stored filename and returns false. Otherwise it sets that state to `2`, stores the request filename, sends an initial `PRINT_COMPLETE` reply, changes the current directory and `QFile` filename, then calls `checkFile`. A second reply maps the check result `1` to `PRINT_END`, `2` to `PRINT_PROCESSING`, and other values to `PRINT_FAIL`; afterward the state becomes `4` and the handler returns true. The JSON dispatcher at `libcxWebsocket.so` `0x19b8c` invokes this method at `0x19dd4` and discards its returned boolean. No direct printer-start or UART call appears in this handler or its dispatcher. Do not treat `START_PRINT` acceptance as proof that the STM32 was commanded to print.

`printPause(QJsonObject)` and `printStop(QJsonObject)` both parse `filename` and `token`, but pass only the token to their corresponding server methods. `CxSslEchoServer::getPrintPauseStatus(QString)` at `0x14aa4` emits `sigDoPrintPause(int&,QString)`; `getPrintStopStatus(QString)` at `0x14b4c` emits `sigDoPrintStop(int&,QString)`. Each initializes the result integer to zero and maps the callback's `1 → 7`, `-1 → 6`, and all other values to `8`. The handlers then use `TRANSCMD::valueToKey`: `6 → PRINT_PAUSE`, `7 → PRINT_STOP`, `8 → GET_PRINT_STATUS`. Thus the text reply retains its request command in `cmd`, while the `status` value is one of those enum names. The pause handler sets `this+0x4c` to `4`; stop sets it to `0`. Neither reply includes the parsed filename.

The `PrinterUI` `WebsocketTransFile` constructor creates a `CxSslEchoServer` on port 18188 and installs 12 typed Qt connection wrappers. The constructor's callsite `0x20caac` loads the signal pointer from GOT slot `0x476014`, whose `R_ARM_GLOB_DAT` relocation names `CxSslEchoServer::sigDoPrintPause(int&,QString)`; the associated direct Qt slot thunk reaches the callback at `0x20b8f4`. The next control connection at `0x20caec` uses GOT slot `0x476ddc`, relocated to `CxSslEchoServer::sigDoPrintStop(int&,QString)`, and its direct slot thunk reaches `0x20ba8c`. Thus the incoming pause request uses the pause callback and the stop request uses the stop callback. The pause callback accepts internal state `+0x84` in `{1,5}` when `+0x30 == 1`; the stop callback accepts state `+0x84` in `{1,5,6}`. Each writes result `1` on acceptance, `-1` for a bad token, and `-2` for a state rejection. The server maps `-2` to enum value `8`. These accepted callbacks emit `WebsocketTransFile::sigPrinterPause()` (`0x20b9b4`) or `sigPrinterStop()` (`0x20bb4c`). A connection onward to `Controller`, the serial scheduler, or the physical pause/stop action is not proven.

`setPrintPara(QJsonObject)` parses six parameter values as strings and also parses a token:

| JSON key | `PrintStatusPara` byte offset |
|---|---:|
| `initExposure` | `+16` |
| `delayLight` | `+20` |
| `printExposure` | `+24` |
| `printHeight` | `+28` |
| `eleSpeed` | `+32` |
| `bottomExposureNum` | `+36` |

The handler passes a copy of that parameter object and the token to the server's `setPrintPara`, which emits `sigSetPrintPara`; this library path shows no parameter validation or direct serial write. It replies with `cmd:"PRINT_PARA_SET"`. The status construction is anomalous: the handler obtains a string from `getPrintStatusKey(para+48)` but does not insert it into the JSON; the `status` field instead comes from `TRANSCMD::valueToKey(para+52)`. `PrintStatusPara`'s default constructor initializes `+0x30` (`+48`) to zero but leaves `+0x34` (`+52`, the serialized status enum) uninitialized.

The downstream setter callback does not repair the serialized field. The request handler constructs its outer `PrintStatusPara` at `r11-0x134` (`0x1d288`), passes it to `CxSslEchoServer::setPrintPara` at `0x1d600`, then later reads the outer object's `+0x34` at `0x1d6bc` for the JSON reply. The server method at `0x14c90` copy-constructs a second `PrintStatusPara` at its own `r11-0x40`, emits `sigSetPrintPara(copy&, token)` at `0x14cd8`, and destroys that copy at `0x14cf4`; no copy-back to the request handler's outer object is present. The matching `PrinterUI` callback can write `6` on token failure, `7` when its setter accepts the values, or `8` when the setter rejects them, but those writes target the emitted copy. It also leaves the status untouched on its separate UI-state-gate failure. Therefore the request handler's serialized `+52` remains uninitialized in the recovered path, even when the UI callback accepts the parameter update. Treat `PRINT_PARA_SET.status` as unreliable stack data, not as an acknowledgement of parameter success.

`PrinterUI` contains a token-checking callback at `0x20be00`. For a bad token it writes `6` at `PrintStatusPara+0x34`; with a valid token and the UI state gate `+0x9c == 1`, it calls the parameter setter at `0x20d3f4` (callsite `0x20bea8`) and tests its boolean result. The accepted branch writes `7` at `+0x34` and emits `WebsocketTransFile::sigSetPrintPara()` at `0x20bed0`; rejection writes `8`. The separate valid-token state-gate failure reaches the callback return without assigning this field. The setter validates `ClipPrintSetPara` and stores the accepted print parameters in UI-managed parameter state. A sibling callback at `0x20bc24` calls `writerPrintStateInfo`, matching the status path.

The `WebsocketTransFile` constructor moves the server object to a worker `QThread` at `0x20ccfc` and starts the thread at `0x20cd10`. Both `PrintStatusPara&, QString` connection wrappers (`0x20dbb8` and `0x20dc40`) pass connection type `1`, `Qt::DirectConnection`, to `QObject::connectImpl`. The callback therefore runs synchronously on the emitting thread while `CxSslEchoServer::setPrintPara` still owns the emitted copy. Callback writes cannot reach the handler's separate outer object.

The two `int&, QString` control signals are now paired to their callbacks by the constructor's ordered connection setup and the ELF relocations. At callsite `0x20caac`, the constructor loads its signal pointer through `.got + 0x1364` (`0x476014`); that slot's `R_ARM_GLOB_DAT` relocation names `CxSslEchoServer::sigDoPrintPause(int&,QString)`. The `0x20daa8` thunk builds the slot object whose invoke path reaches the token/state-gated pause callback at `0x20b8f4`. The next callsite, `0x20caec`, loads `.got + 0x212c` (`0x476ddc`), relocated to `CxSslEchoServer::sigDoPrintStop(int&,QString)`; its `0x20db30` thunk reaches the stop callback at `0x20ba8c`. The intermediate `QSlotObject` invokers and `FunctorCall` functions are `0x20f034 → 0x20f6a4 → 0x20f9dc` for pause and `0x20f0e0 → 0x20f6d4 → 0x20fa6c` for stop. Both thunks pass connection type `1` (`Qt::DirectConnection`), so callbacks execute synchronously on the server's emitting thread. The constructor's PC-relative literal at `0x20cd90` is `0x00268434`; ARM-state PC at the `add` instruction `0x20c874` is `0x20c87c`, giving `.got` base `0x474cb0` and confirming the slot calculations.

Static analysis follows the emitted signals into `PrintFile::PrintFile(QObject*)` at `0x243ec0`, through state entry handlers, and into the asynchronous serial worker. Pause uses `sigPrinterPause()` to transition `state+0x5eb8c → state+0x5eb90` (`0x244ab8`). Entry body `0x24282c` publishes UI/CXY state 6, stops the timer, and sets `SerialPortPrintFile` status 1. `HandleButtonStatus()` at `0x27f310` then calls `pauseMotor()` (`0x2748f8`): after 50 ms it sends `M410 S0 `, then polls `M114 ` about every 200 ms until its result is empty or `OK\n`. `waitRecvMsgFromSerial()` uses `CXSerial::GetRecvMsgFromSerial()`, whose underlying `Serial::readline` reads through LF with a 100-byte maximum; 100 is a length cap, not a timeout. If the CXY flag at object offset `+0x8a` is set and the computed raise distance is positive, it also calls `motorRaiseOrDown()` with a runtime-built move command. The pause helper and this dynamic lift path align with the passive print trace, which recorded M410 S0 and G0 activity during user pauses.

Stop from active states `+0x5eb94` / `+0x5eb8c` reaches final state `+0x5eba8` (`0x2452c0`, `0x245338`). Entry body `0x2436bc` closes `ThreadParseModuleFile` and branches on an unidentified object byte `+0x89`. A nonzero value sets worker status 3, publishes UI/CXY stop state, and starts `PostPrinterInfoThread`; the worker calls `motorForceStop()` (`0x27e8d4`), which sends `M410 S2 ` after 50 ms and polls `M114 ` about every 200 ms until `OK`/`OK1`, then the worker sleeps 50 ms, sends `M114 `, and checks the response. If it is not `Busy\n`, it sends the runtime-built `getMotorMoveUpCommand()` (`G0 Z%1 F%2 D1 S0 H%3 ` for the normal motor profile or `G0 Z%1 F%2 D1 S1 H%3 ` for the external-motor profile), polls `M114 ` about every 100 ms until `OK`/`OK1`, and calls `endToZero()`. If the first response is `Busy\n`, that lift-command branch is skipped. A zero value instead sets status 1 and takes the `pauseMotor()` fallback. Stop from the other two recovered states reaches final state `+0x5eb9c` (`0x2451d0`, `0x245248`); its entry body `0x242e28` closes the parser and shuts down the worker threads without calling the motor-stop helper. This recovers the static UART commands and worker branches, but not the meaning of byte `+0x89`, the contents/effect of the dynamic follow-up move, or the physical stop behavior. No WebSocket pause/stop request was sent to the printer.

## Comparison with Creality-Control / Halot Box clients

Creality-Control's public Home Assistant [status source](https://github.com/SiloCityLabs/Creality-Control/blob/main/custom_components/creality_control/__init__.py) opens `ws://host:18188/`, sends `GET_PRINT_STATUS` with a token, and expects `printStatus`, `filename`, `printRemainTime`, `progress`, `curSliceLayer`, and `sliceLayerCount`. Its [pause/stop buttons](https://github.com/SiloCityLabs/Creality-Control/blob/main/custom_components/creality_control/button.py) use the same `PRINT_PAUSE` and `PRINT_STOP` words. The CL-60 binary and a live authenticated status response confirm the same request, transport, token recipe, and all of these fields except `progress`.

This is a live-confirmed status path, though full client compatibility remains unverified: the response omits `progress`, and pause/stop/upload/start-print behavior has not been exercised through WebSocket. Static pause/stop paths now resolve to `M410 S0`, `M410 S2`, `M114` polling, and a runtime-built `G0` lift template; substituted values and physical effects remain unverified. The request used the encrypted token already stored by the printer; no plaintext configuration value was exposed or retained. The public compatibility tracker still has no completed model-specific HALOT-ONE test.

## File upload data path

`START_FILE` reads `filename`, `size`, `offset`, `key`, and `token`, then passes the token to the server's transfer-status check. The request's `offset` is parsed but not used. A fresh transfer creates or truncates the fixed temporary file `wifi_tranfer.tmp`, sets `received` to zero, and stores the requested filename and opaque transfer key.

The static resume path is disk-backed. On disconnect, `onDisconnect()` closes the temporary file and `saveKeyInfo()` writes a QDataStream v18 footer at byte offset equal to the declared file size. The footer fields are `qint64 size`, `qint64 received`, `QString filename`, and `QString key`. For an existing temporary file, `getKeyInfo()` seeks to the size in the new request and reads this footer. The handler accepts the resume only when the supplied key exactly equals the stored key, then returns the stored received count as the response's string-valued `offset`. A key mismatch falls through to fresh initialization, replacing the partial transfer. The request's own offset remains ignored. Because lookup seeks using the newly requested size, a reconnect appears to require the original declared size; this path does not validate the stored size, filename, or QDataStream status. The binary behavior is recovered, but no real client reconnect/resume has been attempted.

**Upload side effect recovered statically:** both the fresh setup path and the accepted-resume path call `removePcModelFile(outDir)`. That routine removes regular files ending in `.cxdlp`, `.cxline`, or `.bak` from the transfer output directory. Completion also removes the destination filename before renaming the temporary file into place. No live upload was attempted because even `START_FILE` can delete existing jobs or backup files in its output directory; its exact live contents were not inspected.

Each complete WebSocket binary message is passed as a `QByteArray` to the active `CxFileTransHandle`. `processBinary()` does not parse an application-level header from the message. It seeks the output file to the current `received` offset, then writes the message bytes directly. The handler constructor initializes its compression flag to `true`, and no other store to that member appears in this library. `processBinary()` therefore calls Qt `qUncompress()` on each message by default; the `START_FILE` reply exposes that flag as `compress: true`. This means the sender is expected to use Qt's `qCompress()` byte format, which carries a four-byte big-endian uncompressed-size prefix before the zlib stream. The stream is set to QDataStream version 18, but the payload is written with `writeRawData()`, so this setting does not add framing to the bytes. See the [Qt QByteArray qUncompress reference](https://doc.qt.io/qt-5/qbytearray.html#qUncompress).

After a successful chunk write the printer sends a text JSON acknowledgement with `cmd: "START_DATA"`, `filename`, numeric `rcode: 0`, and string-valued `size` and `received` fields. `filename` carries the per-transfer `key` value from `START_FILE`, and `received` is the cumulative file offset after the write. If opening the output file fails, the recovered error branch sends `errorcode: 2`.

When `received` reaches or exceeds the declared `size`, the handler closes and truncates the temporary file to the declared payload size (removing the footer), removes any existing destination of the requested filename, and renames the temporary file to that name. It then emits the `finish()` signal and sends `CHECK_DATA` with the request transfer key and numeric `checkstate`. `finish()` is signal plumbing in this library, not an in-library content hash or checksum; downstream validation is unresolved. The binary establishes cumulative offsets, per-message acknowledgements, and a static resume mechanism, but the sender's chunk boundaries, retry policy, reconnect behavior, and downstream file validation have not been tested.
