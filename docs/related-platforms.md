# Related Creality resin platforms and open firmware

Research snapshot: 2026-09-30. This page compares the HALOT-ONE CL-60 evidence collected in this repository with public work on other Creality and resin-printer platforms. “Same ecosystem” below means shared file formats, tools, or software patterns; it does not imply pin, MCU, or firmware compatibility.

## What the HALOT evidence actually proves

The inspected CL-60 runs a Creality Linux host and a separate STM32 controller. This project has recovered a fixed-frame host UART protocol, including `M678`, `M114`, `M410`, and status replies, and traced the exposure image path through H616 HDMI and an RK628 bridge to MIPI DSI. Those results are specific to the installed CL-60 image and the one physical unit.

The local 2.303.1 `halotMachine.xml` and `PrinterUI` build contain profiles for multiple Creality machine identifiers, including `CL60`, `CL79` (HALOT-ONE PLUS), `CL89` (HALOT-SKY), `CL89D`, `CL89L`, `CL133`, `CL130`, and other variants. The profiles select different serial model types and display/output configuration. For example, CL60 maps a 1620×2560 source image to 540×2560; CL79 maps 4320×2560 to 1440×2560; CL89 maps 3840×2400 to 1280×2400. All three profiles use the same `LCD` image backend, but specify different pixel sizes and mechanical settings. This proves the **same inspected host application build contains multi-model branches and geometry conversion**, not that the panel electronics or serial controller are identical. The profile field `SendSerialModelType=E` for CL60/CL79 also differs from the separately captured `MODELS:A` handshake command; these must not be conflated as one MCU selector.

There is public evidence for a common Creality file ecosystem: UVtools implements CXDLP/CXDLPV4 and has PrusaSlicer profiles for HALOT-ONE CL-60, HALOT-SKY CL-89, HALOT-LITE CL-89L, HALOT-ONE PLUS CL-79, and HALOT-ONE PRO CL-70. These older models use the CXDLP family in those profiles; the HALOT-MAGE CL-103L profile uses CXDLPV4, while LD-002R/H profiles use CTB. The CL-60 profile declares 1620×2560 display pixels and HALOT-specific file-format tags. UVtools maintainers also report that some CXDLP settings are ignored by the printer in favor of settings stored in the printer UI/firmware. That is useful for the **job-file and slicer layer**, but it does not establish that layer metadata maps one-to-one to the STM32 `M678` parameters.

The CXDLP generation is a separate compatibility boundary. The job recovered from this CL-60 after the 2026-09-28 print is 10,270,850 bytes (SHA-256 `3012a35100c5e16c72fffd1d909c3f6494d2ce797e11a131ffb87a3b4c3e971f`); its header starts `CXSW3DV2`, identifies `CL-60`, and declares 1620×2560. The inert offline reader decodes its 1,591 layers, and the passive print trace records all 1,591 layer transactions for that job. In UVtools Discussion #391, the maintainer says V1 is no longer supported by newer UVtools and that V2/V3 selection depends on the printer firmware; a later reply notes that some Halot One units require V2. This is a community compatibility report, not an official Creality firmware matrix. It supports V2 as the observed format for this 2.303.1 unit, but no V3 job has been tried on it. Job-file version support does not establish compatibility of the UART frame, `M678` semantics, or display hardware.

An independent 2021 HALOT-SKY teardown reports the same broad architecture class as this CL-60: Linux/OpenWrt host, separate STM32F103 motion controller, and HDMI-to-MIPI monochrome-panel bridge. Its identified host SoC is Allwinner H6 and its bridge is Lontium LT6911C; this CL-60 has H616 and RK628 according to our live software/device evidence. This is strong evidence of a shared design pattern in an older HALOT branch, while the changed SoC and bridge are reasons not to assume identical binaries or display protocol.

### Package-level evidence across older HALOT models

The official HALOT-SKY, HALOT-LITE, HALOT-ONE PLUS, and HALOT-ONE PRO download pages resolve their `V1_H2.238.2a2.238.2_C2.238.2_R2.238.2` entries to the **same CDN object**, not four merely similar filenames. The shared archive is 130,822,607 bytes with SHA-256 `b80147dcd1f47d8124bef7b90d9cd6c23ce2af3f16c78a16b7ed737d94c31d57`. Its SWU contains a TinaLinux rootfs and a single `/etc/V1-01.bin` STM32 updater image. The extracted MCU image is 31,248 bytes, SHA-256 `379470dd8afe47b152cabdedcd6c983b1fc112c07d164a18d8d0fbb89677f319`. Thus these four official download entries served the same host and STM32 payload at this release point. That is direct package identity evidence; it does not establish identical mainboards, wiring, panel timing, or safe interchange of the complete printer configuration.

These four official download entries served the same 2.238.2 package. That finding should not be generalized to every Creality resin model: the inspected MAGE S/PRO packages use a `ChituUpgrade.bin`-based U-Boot/NAND/UBI updater. The separate plain-MAGE `V466_2.5` ZIP is a USB bundle whose `update.LCD` invokes `M6030` for named UI, FPGA, and parameter files, then `M6033`; its archive does not have the S/PRO package layout. No sibling-model live UART capture has yet confirmed the CL-60's runtime protocol on another machine.

An older 2022 OTA package provides an additional historical comparison. The archive linked by the independent HALOT-ONE rooting write-up is hosted on Creality's CDN under its `cl89` path; the downloaded archive is 94,894,124 bytes, SHA-256 `9080ddea1e9f16462793cbe595be44bbba01c81df615eb5ad87c67ab581bb05c`. Its rootfs contains a `CL60` profile in `halotMachine.xml` with the 1620×2560 source and 540×2560 compressed geometry, and a `PrinterUI` binary containing the same `M678 Z%1 U%2 D%3 T%4 P%5 M%6 L%7` host template as the later CL-60 builds. The bundled STM32 `/etc/V1-01.bin` is 11,332 bytes, SHA-256 `c04f84418b9cea9e6e7483f2a255dc7a019bc539e127febe250aba7de4649267`, with visible `V1.21`, `M678`, and `M114` strings; it is not byte-identical to either the shared 2.238.2 payload or the installed 2.303.1 `SWV1.89` image. The old updater script selects GPIO `PA6` for BOOT0 and `PA0` for reset, flashes `/etc/V1-01.bin` at `0x08000000` through `/dev/ttyS2`, then configures that port for 115200 baud. Those script names document the vendor's software routing, not verified connector pins or safe cross-model flashing.

The older STM32 image also contains the literal `M678 Z5 U10 D` alongside `M678` and `M114`; this confirms command-vocabulary continuity in an earlier CL60-profile package, but does not recover the units or semantics of those fields. The article independently records a live unit identifying itself as `CL60` and links this OTA object; the `cl89` URL path alone should not be treated as the hardware model or proof that every model in the rootfs used the same MCU image.

The 2.238.2 image was extracted temporarily for this comparison and was not added to the repository. The later 2.303.1 image is the one already analyzed locally. This comparison makes the lineage more specific: the 2.238.2 download used for SKY/LITE/ONE PLUS/ONE PRO contains a multi-model TinaLinux `PrinterUI` build with CL60 and CL89 profiles and a CL60-style M678 template; the later CL-60 2.303.1 build retains those model labels/template and the byte-identical RK628 driver, while its host app, rootfs, kernel, and STM32 image changed. The selector branch and sampled M114/M410 code are closely related across revisions; M678 retains the common parser/event structure, while its newer optional `P2` suffix path was not observed in ordinary CL60 layer traffic. Static comparison of `PrinterUI::lcdPrint` and its command builders shows the same layer call order and field construction across these two host builds (details below). A direct instruction-level comparison now also confirms that the M678 state-machine worker and TIM3 core were retained across the STM32 revisions. This proves static code continuity, not identical helper behavior or physical effects. No independent raw STM32 UART trace from a second retail model was found.

#### STM32 M678 worker and TIM3 comparison

The V1.821 STM32 from the official 2.238.2 package and the local V1.89 STM32 were compared as raw Thumb images mapped at `0x08000000`. The worker extents were decoded with Capstone in Thumb/M-class mode; instruction comparisons preserve mnemonic, registers, immediates, PC-relative literal displacement, and internal branch offsets, while normalizing build-specific external call destinations.

| Component | V1.821, 2.238.2 | V1.89, 2.303.1 | Comparison |
|---|---|---|---|
| M678 state-machine worker | `0x0800433c`–`0x08004631` | `0x080046f0`–`0x080049e5` | Both extents are `0x2f6` bytes. Excluding the 8-byte inline `TBB` jump table, each contains 310 decoded Thumb code instructions; all 310 same-index instructions match after normalizing external call targets, and the table bytes also match. The eight-way state dispatch and internal control-flow offsets are retained. Of 74 PC-relative literal references, 66 resolve to relocated RAM globals; the remaining eight resolve to identical values. |
| IRQ 29 / TIM3 callback | `0x0800258c` | `0x080028c8` | Each decoded function has 99 instructions, with the same normalized instruction sequence. The counter, phase thresholds, active flag, and 64-bit tick fields are relocated by +8 bytes in V1.89. |
| TIM3 initializer | `0x080026b4` | `0x080029f0` | Each decoded function has 39 instructions and the same normalized sequence. V1.821 calls it at `0x080042ac` with `(1000, 720)`; V1.89 calls it with `(1000, 0x2d0)`. Both subtract one and configure ARR 999 / PSC 719 for TIM3 at `0x40000400`, with IRQ 29. |

In the older worker, the ten-sample `L` history occupies `0x200000e0`–`0x20000104`, with its average at `0x20000108`; V1.89 uses `0x200000e8`–`0x2000010c` and `0x20000110`. Both workers use `q = floor(avg(L)/1200)`. Each separately divides `P` and `M` by 10 and converts the intermediate results: the older completion threshold is `trunc(P/10 − M/10) + 100q` at `0x20000064`, and its early threshold is `100q − M/10` at `0x20000068`. These correspond to the V1.89 thresholds at `0x2000006c` and `0x20000070`. The other resolved pointer relocations are the worker's timer block (`0x200001dc` → `0x200001f0`) and the M114 event-handle slot (`0x20000018` → `0x2000001c`).

This is strong evidence that the layer scheduler and timer callback algorithm were carried forward almost byte-for-byte, with RAM globals moved and external helper calls left to each build. It does not prove those helper implementations are identical, establish the HSE frequency, or identify board-level pin and load behavior. The shared 2.238.2 package contains multiple model profiles, but no second-model raw UART or physical timing capture independently validates this state machine on another retail printer.

The V1.21 comparison used raw-image string references and Thumb disassembly (Capstone, M-class mode), not dynamic execution. Field names for its seven slots are mapped from the companion 2022 `PrinterUI` template, not recovered independently from all old MCU code. For old `M108`, exact pin masks and space separators are static evidence; the two formatter calls appear to form one `108 n n n\n` reply, but this was not confirmed on the wire. The V1.21 absence of M800/M355 strings and USART3/DMA address literals is negative static evidence. The 31,248-byte V1.821 image was extracted from the [official Creality package](https://file2-cdn.creality.com/file/63c45268ee001da26529f5f3629f7834/V1_H2.238.2a2.238.2_C2.238.2_R2.238.2.tar.gz); its SHA-256 is `379470dd8afe47b152cabdedcd6c983b1fc112c07d164a18d8d0fbb89677f319`, and its embedded version string is `SWV1.821`. It was statically disassembled without retaining the vendor binary in the repository. Its referenced M800/M355 handlers show that the auxiliary paths existed by this release and reveal the four-state-to-seven-stage M800 change. The V1.821 M678 handler at `0x08005c62` parses the same seven parameter slots, while V1.89 relocates the storage and adds a `P2` suffix branch. These results strengthen software-lineage evidence while also showing that reply strings, field widths, GPIO sources, globals, and some command branches evolved; they do not establish cross-version wire compatibility or physical semantics.

#### Three-release M678 worker and timer lineage

The V1.21 worker at `[0x08002294, 0x08002574)` is 299 decoded Thumb instructions and uses states 0–3. Its state-2 path keeps a ten-word `L` history at `0x2000015c`, the average at `0x20000184`, and the sample index at `0x20000201`. A new sample below the stored average fills all ten history words with that sample; otherwise the code sums the history, then divides by ten to update the average. State 3 divides the average by 1200 and combines that term with separately divided `P/10` and `M/10` to build the TIM3 thresholds. This confirms that the filtered-`L` schedule was already present in V1.21.

The V1.21 worker also derives its early and completion thresholds from the same `q = floor(avg(L)/1200)` term and the separately converted `P/10` and `M/10` values. Its IRQ 29 callback calls the `0x52,0x04` and `0x52,0x00` output helpers at threshold transitions, linking that software pattern to the later images' matching command primitive; the physical endpoint and effect are still unverified. The V1.21 image SHA-256 is `c04f84418b9cea9e6e7483f2a255dc7a019bc539e127febe250aba7de4649267`; the V1.821 and V1.89 hashes are recorded above.

The decimal numeric-token path used by the `M678` field parser is substantially retained across all three STM32 images. The 54-byte setup routines at V1.21 `0x08000504`, V1.821 `0x0800074c`, and V1.89 `0x08000754` each decode to 23 Thumb instructions with the same normalized sequence. The following 90-byte conversion wrappers at `0x0800053a`, `0x08000782`, and `0x0800078a` each contain 40 instructions and likewise match after normalizing their build-specific `BL` targets. The wrapper initializes an eight-byte result area and passes the token through the same register/stack layout.

The wrappers call scanner bodies at V1.21 `[0x080007b4, 0x080009de)`, V1.821 `[0x08000b48, 0x08000d74)`, and V1.89 `[0x08000b50, 0x08000d7c)`. They are 554 bytes/228 instructions, 556 bytes/229 instructions, and 556 bytes/229 instructions respectively. The apparent one-instruction difference is the branch to a shared return epilogue outside each scanner range; after representing that common exit consistently and normalizing external calls, the scanner instruction streams match. The downstream significand/exponent-to-binary64 routines are each 296 bytes/119 instructions and match under the same call-target normalization. The binary64 multiply helper (228 bytes/69 instructions), divide helper (222 bytes/74 instructions), integer-to-binary64 helper (156 bytes/62 instructions), and seven-instruction digit classifier also have matching normalized bodies. One narrower conversion step differs: V1.21's double-to-float helper is 74 bytes and performs tie-to-even rounding inline, whereas V1.821 and V1.89 use a 56-byte helper that calls a separate rounding routine. That refactor's exact rounding equivalence and all converter literal-pool values are still being checked. This is strong static evidence that the decimal scanner and binary64 arithmetic were carried forward, but it does not yet prove identical final float rounding or every malformed-token edge case.

### Shared Allwinner update framework, different controller payloads

The CL-60 and HALOT R6 packages share part of the **Linux update mechanism** even though their controller/display payloads diverge. The official R6 C2.306.5 outer archive (SHA-256 `aefe16490a876bab57b2d71efaa52a6d727a4c4bb8aa4ed2f60a8ff9f1fd0dc5`) wraps `tina-r528-R004.swr`; its inner CPIO manifest uses the same broad `upgrade_recovery` → reboot → `upgrade_kernel` → `upgrade_usr` staging and the Allwinner `awuboot` handler seen in the CL-60 2.303.1 SWU. Both direct the kernel and rootfs writes to named eMMC partitions.

The target layouts are not interchangeable. R6's manifest additionally writes a dedicated `/dev/by-name/dsp0` partition with a 290,540-byte Xtensa ELF32 image (SHA-256 `e65e7e19a202c3338d6220046636bf2624fc8eed2366c876826b3e0bbf50f51e`). The inspected CL-60 package has no `dsp0` member or partition; its MCU firmware is `/etc/V1-01.bin` inside rootfs and its boot-time updater sends it to the STM32 over `/dev/ttyS2`. So the commonality is the Allwinner/SWUpdate orchestration layer, while the R6 DSP/RPMsg controller path and CL-60 STM32/UART path are different. Shared `awuboot` code is evidence of a related host/update family, not permission to cross-flash either package.

### PrinterUI cross-version comparison

The 2.238.2 and 2.303.1 `PrinterUI` executables have different hashes, but their active CL60 layer path is strongly aligned: `lcdPrint` is 5,528 bytes in both and retains the same call order—compute `L`, select the initial or regular `M678` builder, submit the BGRA image, send the command over UART, then poll `WaitMotorStatus`/`M114`. The three `M678` builder functions also retain the same sizes and instruction shape, and both builds use the same `M678 Z%1 U%2 D%3 T%4 P%5 M%6 L%7 ` template. This is static code equivalence evidence, not a second-model runtime trace.

The host-side data sources are also mapped: `Z` comes from CXY offset `+0x18` (`PrintHeight`); `U` and `D` both come from `+0x1a` (`EleSpeed`); `T` comes from the layer/job field; initial-layer `P` is `InitExposure × 1000`, while regular-layer `P` is the CXY exposure value at `+0x04 × 1000`; `M` is `DelayLight` at `+0x20 × 1000`; and `L` comes from `GetCurLayoutArea`. `ThreadWorkIOT::message_arrived` also accepts numeric JSON properties that call the CXY setters for initial/regular exposure, delay-light, electric speed, and print height. The private post-print UDISK log now records the job's initial CXY state and in-job parameter changes that align with successive transmitted M678 tuples: initial `PrintHeight=5`, `InitExposure=40`, `PrintExposure=3.3`, and `EleSpeed=3`, then runtime values corresponding to `Z10`, `P4200`, and `U/D=2`, followed by `Z5`. The log captures the host's current/outbound attribute values, not an inbound setting message or the operator action that changed them. In particular, the CL60 XML defaults `PrintHeight=6` and `EleSpeed=1` are not the effective per-layer values from that print.

The two XML files contain the same 35 machine IDs; the complete serialized subtrees match for CL60, CL89, CL89L, CL60RS, CL79, and CL70. Four retail profiles resolve as follows in both releases: HALOT-SKY/CL89 uses serial type `A` and 3840×2400→1280×2400; HALOT-LITE/CL89L uses `E` and the same geometry; HALOT-ONE PLUS/CL79 uses `E` and 4320×2560→1440×2560; HALOT-ONE PRO/CL70 uses `E` and 2400×2560→800×2560. Each specifies LCD/BGRA output and 3:1 horizontal compression. The control CL60 row is `E`, 1620×2560→540×2560. These profile identifiers and `SendSerialModelType` values are separate from the MCU's `MODELS:` handshake byte.

The 2.238.2 and 2.303.1 `PrinterUI` binaries both contain only the host template `M678 Z%1 U%2 D%3 T%4 P%5 M%6 L%7 `; neither contains a `P2` suffix or the inspected DSP/RPMsg endpoint tokens. The 2.303.1 STM32 parser's optional `P2` branch is therefore an MCU capability, not an extension emitted by these two host builds. R6's separate `C%7`/conditional-`P2` path must not be generalized to the older HALOT profile family.

#### 2022 `SerialPortPrintFile::run` call path

A focused disassembly of the `PrinterUI` extracted from the [2022 official OTA archive](https://file-cdn.creality.com/ota-sz/cl_h7_firmware/beta/cl89/cx7_v2.202.28_app_v2.202.28_beta.tar.gz) (2,352,344 B; SHA-256 `c61c748e3bb88eea090d201c32f14cf270d4039daff6e118782ce9beb8e4e23d`) recovers an older layer-worker path. `SerialPortPrintFile::run()` is at `0x00153a3c` (13,852 B). Its first-layer builder, `getPrintFirstPictureCommand()` at `0x00159ef0`, stores the command at object offset `+0x44`; the regular-layer builder, `getPrintOtherPictureCommand(float)` at `0x0015a3ac`, stores it at `+0x5c`. Both use the `M678 Z%1 U%2 D%3 T%4 P%5 M%6 L%7 ` template. In `run()`, the first-layer branch sends the prepared `+0x44` string through `CXSerial::SendMsgToSerial` at `0x001553e0`, and the regular-layer branch sends `+0x5c` at `0x0015544c`. The worker's later `SendBgraImage` calls occur at `0x00155588` and `0x00155b8c`; these are branch-dependent calls, so the disassembly should not be read as a simple unconditional one-call-per-layer sequence. In the shown worker path, the command send precedes the later image-submission call.

The old `SendBgraImage(int,int,bool)` helper at `0x000f1860` initializes its `YuvDataSend` context as needed, enables the display output port, and delegates to `YuvDataSend::sendRgbaDataToHdmi(false)` at `0x00118088`. This confirms the old host's HDMI-named output call path, not the specific physical panel latch event.

The worker calls `waitRecvMsgFromSerial` at `0x001555c0` after the `0x00155588` image call. The waiter at `0x0015c1b4` sleeps 12 ms between `CXSerial::RecvMsgFromSerial` reads, checks M114-related response text (the `M114 ` literal is referenced at `0x0015c37c`), and retries its second string argument through `CXSerial::SendMsgToSerial` at `0x0015ccd8` after five iterations. The retry argument at this per-layer callsite is copied from a local `std::string` initialized empty at `0x00153af8`; no assignment before the call was found. Therefore the waiter and M114 response handling are present, but this callsite does not establish that the five-iteration retry sends `M114`, nor does it establish a periodic M114 query for each layer. `run()` contains direct M114 sends in separate initialization and recovery paths.

This differs from the installed CL-60 2.303.1 `SerialPortPrintFile::lcdPrint()` path at `0x00274d64`: that path submits the parsed image with `SendBgraImage`, then sends the per-layer M678 command and waits through `WaitMotorStatus`/M114. The 2022 worker sends the prepared M678 command before its later branch-dependent image-submission call. This is a difference in host call order across the two builds despite the shared M678 format string. It does not prove when either build's image was electrically latched or became visible on the monochrome panel; neither `SendBgraImage` nor the HDMI-named function establishes panel timing or VSYNC synchronization.

### R6 cross-target binary check

The R6 C2.306.5 app confirms a shared Creality host-application family, but also shows why matching model labels cannot be treated as proof that its controller firmware applies to CL-60. `/etc/machine.json` identifies this package as `R004` (`version=2.306.5`, `appid=cl_h7_firmware`), and its `[R004]` profile sets `IsDspCommunicate=true`, `SendSerialModelType=B`, and `SerialName=ttyS2`. The embedded `[CL60]` section selects 1620×2560→540×2560, HDMI/BGRA, `ttyS2`, and serial type `A`, but omits `IsDspCommunicate`; the getter supplies false when the key is absent. The profile parser can then overlay `/device/config/userMachinePara.ini` if that private file exists, so the package describes defaults rather than proving live runtime state. The installed CL-60 profile uses type `E`, showing these config values differ by build. Neither `A`, `B`, nor `E` should be conflated with the captured `MODELS:A` handshake byte. No live R6 runtime configuration or transport trace was captured.

This DSP flag is not unique to the R6 profile. In the same C2.306.5 ini it is explicitly true for these profiles:

`IsDspCommunicate` is absent from `[CL60]` (`HALOT-ONE`) and `[CL89]` (`HALOT-SKY`), whose image paths are `HDMI`; the getter therefore defaults to serial unless private user configuration overrides it. The ini comment describes `SendSerialModelType` as an MCU/DSP mode type, but the binary uses the separate `IsDspCommunicate` boolean for its actual transport branch. This establishes that one Creality host build carries both transport backends and several image-output modes across a wider set of machine profiles. Except for names explicitly matching products, the profile IDs here are not independently mapped to retail models or physical boards.

The R6 `PrinterUI` is ARM32 hard-float. Its `CXPrintFileCxdlpv4::motorMove(bool,float)` method at `0x0016ea94` loads the `M678 ... C%7` template at `0x16ede4`, substitutes seven values through `QString::arg`, and calls `CXSerialManager::GetMsgByCmd` at `0x16f194`. The manager branches between `CXDsp::GetMsgByCmd` and `CXSerial::GetMsgByCmd` according to `IsDspCommunicate`; the package-matched R004 profile sets this flag true, while the embedded CL60 profile omits it and therefore selects serial if active. An argument-level trace recovers the source of `C`: `CXPrintFileCxdlpv4::parseOnePrintImage()` at `0x16dd38` reads the uint32 at per-layer `LayerDef+0x18` (`0x16dee4`–`0x16df08`) into a vector; `startPrintProcess()` at `0x155e74` selects the current layer's element (`0x1566e0`–`0x156734`), converts it to float, and dispatches through vtable slot `+0x4c` to `motorMove(bool,float)`. The method formats that float as field 7 at `0x16f010`–`0x16f054`; there is no arithmetic scale/normalization in this data path, though the float-to-text formatting still determines its wire spelling. Its adaptive branch also passes a reference to this value into `calculateAdaptiveParameters`, which reads it into its adaptive list but does not change it. R6's `libcxdlp.so` deserializer places `DataType` at `+0x14`, the `C` source at `+0x18`, and the next uint32 at `+0x1c`; the third-party [UVtools CXDLPv4 schema](https://github.com/sn4k3/UVtools/blob/master/UVtools.Core/FileFormats/CrealityCXDLPv4File.cs#L2831-L2889) names those last two fields `CentroidDistance` and `LargestArea`, respectively. Thus the host-side source slot for R6 `C` is recovered, and the `CentroidDistance` label is supported by that schema. The DSP parses its fixed-slot numeric value into context `+72/+76`, where case 4 routes it to marker-specific histories. No live R6 trace establishes the input's physical units or the resulting device behavior.

This R6 field is distinct from CL60 `L`. Both the shared HALOT 2.238.2 and local CL-60 2.303.1 host builds use `L%7`: their `lcdPrint` paths call `GetCurLayoutArea(layer)` and pass its float result to the initial-layer or regular-layer command builder. In the shared C2.238.2 `PrinterUI` (`GetCurLayoutArea` at `0x001b0cb0`) and local 2.303.1 CL-60 binary (`0x001bf478`), the method is 452 bytes; its 106-instruction ARM body matches after masking version-relocated `BL` targets. Both builds use the same `0.05` binary64 and `1000.0f` binary32 literals. Index 0 returns `(width × height) × 0.05 × 0.05`; later indexes select the unsigned CXDLP v3 area-table entry at `index % table_size` and divide it by `1000.0f`. For the local 1620×2560 job, all 1,590 noninitial transmitted values match the corresponding table entries after that division. This is confirmed host-code lineage across the shared release and the installed CL-60 generation, not binary identity or proof of identical STM32 behavior. The R6 `C` source is instead the CXDLPv4 `LayerDef+0x18` slot, separate from `LargestArea` at `+0x1c`, and its host path does not apply CL-60's `/1000` scaling. Do not rename `C` to `L`, reuse CL-60's scaling, or infer equivalent STM32/DSP behavior from the similar command shape. R004 emits `C`; the DSP parser also recognizes `L`, but no user-facing selector for changing the emitted marker was recovered. After building the seven fields, `motorMove` checks a separate byte at config offset `+0x18c`; if nonzero, it appends `P2 `. This is independent of `IsDspCommunicate` and of the `C` value. R6's `waitMotorArrivalPosition()` also constructs `M114`, sends it through `OnlySengCmd`, and reads through `onlyGetMsgfromSerialOrDisp`.

The R6 download page currently lists `V1_H2.238.2_C2.305.26_R2.305.26_R004.tar.gz` (dated 2024-10-09); a separate official C2.306.5 CDN archive was also inspected. The C2.306.5 archive is 57,636,363 B (SHA-256 `aefe16490a876bab57b2d71efaa52a6d727a4c4bb8aa4ed2f60a8ff9f1fd0dc5`). Its embedded `tina-r528-R004.swr` is 58,548,736 B (SHA-256 `9117ef3ea97025e26a9793af3ef45a10639fbd759fe502b00db987a8a282af25`; the config's `swrMd5Value=64682b563a0477c2e4bb5bab3d663c15` matches its MD5). Its update manifest stages kernel, rootfs, and `dsp0` to `/dev/by-name/boot`, `/dev/by-name/rootfs`, and `/dev/by-name/dsp0`, respectively. The `dsp0` member is a 290,540-byte Xtensa ELF (SHA-256 `e65e7e19a202c3338d6220046636bf2624fc8eed2366c876826b3e0bbf50f51e`) containing `SWV1.00.6`, `MODELS:A`, `M114_OK`, `M410_OK1`, and `M678_Busy`. This is a separate DSP image, not the CL-60 STM32 image. R6 rootfs has `mcu_tool`, `stm32flash`, and a 3,103-byte `stm32_update` script, but does not include `/etc/V1-01.bin`. The script selects `/dev/ttyS2` for R004, prepares BOOT0/reset GPIOs, and invokes the STM32 flashing path; it is byte-identical to the old shared HALOT package (SHA-256 `9e230f6fe59b2062d7352aaf880a343917a7fb178e4d2866239a232a81406a1d`). R6 `mcu_tool` is 21,932 B (SHA-256 `fab5ae6387e10eb6264e868fbcca420b4d1b21975ca70b0b7e5c96f2c334b139`), differing from the old package's 17,840-B tool (SHA-256 `221a9c20825dc601ae9c43e18fb813be49a9a1d6e2ed06be4b696a2a341308d3`). This looks like updater scaffolding reused across targets, not evidence that the same STM32 firmware is installed or executed on R6. No R6 UART capture confirms the meaning or behavior of these shared tokens.

A byte-level comparison of the official C2.305.26 and C2.306.5 R004 packages confirms DSP lineage without binary identity. The older archive is 54,345,033 B (SHA-256 `5d1c1da5baad3960f080d044126b1ae995fd9973bba75c7e208616093bac7b4a`); its embedded SWR is 55,140,864 B (SHA-256 `3a12df6f53f1a35d60c8eed66777ccbed30efb51a0a6ffb514d8b84b10e99df6`) and its `dsp0` is 290,284 B (SHA-256 `430e3627749a8a0169eea519b0e4a205c8a9825824e950f7dffb03f9ded9c830`). Both `dsp0` images are little-endian ELF32 Xtensa executables with entry `0x400660` and the same `MODELS`, `SWV1.00.6`, `M114_OK`, `M410_OK1`, `M678_Busy`, and `P2` strings at matching file offsets. The `.text` sections differ substantially: 106,464 B vs. 106,528 B, with 98,880 differing bytes in their common span. Yet the decoded `P2` parser structure and ID 139/140 dispatches match at corresponding locations, shifted by the version's layout (older around `0x3200d37c`, `0x3200d45c`, `0x3200d7d2`; newer around `0x3200d35c`, `0x3200d43c`, `0x3200d7b2`). This supports a stable protocol branch across these two R6 releases while leaving unrelated DSP changes and live RPMsg behavior unresolved. The decoder is a public HiFi4-capable Xtensa toolchain rather than verified vendor Cadence/Allwinner binutils; the ELF itself reports generic Xtensa metadata, so instruction decoding is strong static evidence, not vendor-certified ISA identification.

The R6 mailbox is a separate transport from the CL-60's fixed-frame UART. In the C2.306.5 rootfs, `libdsp_msgbox.so` is a 17,660-byte ARM shared object (SHA-256 `6a149ee21cfefd37d01cf9ed479a0c01d08c4b8e4df6929f01eed19264ac7d01`). Its exported `DspMsgboxSend` at `0x1ee0` converts the numeric message ID to decimal and formats the host-to-DSP envelope with `STA:%s:%s%s`, passing the ID text, payload, and `EOF` as the three substitutions. Thus the host-generated form is `STA:<decimal-id>:<payload>EOF`, with no separator inserted before `EOF` by this routine. `DspMsgboxRecv` finds `STA:`, parses the ID up to the next colon, then copies the rest of the message into its payload buffer; this library layer does not strip `EOF` or trim payload whitespace. The DSP's own format string at VMA `0x3200244c` is `%s%d:%s %s`, which does insert a space before its `EOF` argument. In the R6 `M678` substring branch (`0x3200d78e`–`0x3200d7ac`), the arguments are `STA:`, the context message ID, `M678_Busy`, and `EOF`. This proves a directional formatting difference at the two static endpoints, but no live RPMsg trace is available to show the complete exchanged bytes after the caller processes the returned payload.

The R6 DSP has the same visible command/reply vocabulary as the CL-60 STM32 image: its `M678` path references `M678_Busy`; its command dispatcher references `M114` and formats `M114_OK` and `M114_OK1`; a separate event path references `M114_DELATLIGHT_OVER`. The strings are backed by handler references in the C2.306.5 `dsp0` image (SHA-256 `e65e7e19a202c3338d6220046636bf2624fc8eed2366c876826b3e0bbf50f51e`), rather than only appearing in an unreferenced string scan. R004's `IsDspCommunicate=true` routes `GetMsgByCmd`, send, and receive through `CXDsp`; a missing flag in the embedded CL60 profile defaults to `CXSerial`, subject to the private user-config override described above. The shared inner vocabulary supports software lineage, while the outer RPMsg envelope, `M678` final field (`C` on R6 versus `L` on CL-60), and controller implementation differ. Do not treat token-name overlap as wire or motion compatibility.


The R6 DSP `M678` branch is now instruction-level mapped with the public `xtensa-hifi4-elf-objdump` from the [YuzukiHD HiFi4 toolchain release](https://github.com/YuzukiHD/FreeRTOS-HIFI4-DSP/releases/tag/Toolchains). The tool archive SHA-256 is `81b7cfbcf962e1c5dad51cd20243e63a6f500359e955b30d284727403be36ae4`; the `objdump` binary SHA-256 is `17fe6aaa37442eec18278a6161b98ccd3f1faa5b4ebf5fa68c2e3f1ff14f5534`. The image's `.xtensa.info` identifies `CORE_NAME="aw_axi_cfg0"`, `HW_VERSION="LX7.1.4"`, and `RELEASE_NAME="RI-2020.4"`. This Hifi4-capable decoder produces coherent FLIX instruction boundaries for the relevant code, but an exact Allwinner TIE configuration has not been independently confirmed; treat this as validated static disassembly for the analyzed region, not a fully matched vendor toolchain.

In the R6 DSP parser at `0x3200d7d8`–`0x3200d7ec`, a fixed-slot value from buffer address `0x32028f37` is parsed into context `+72/+76` before any marker search. By positional alignment with the host's seven-field `M678 Z U D T P M C` template, this is the numeric C value. The same handler searches and stores `U`→context `+24/+28`, `D`→`+32/+36`, `Z`→`+40/+44`, `T`→`+48/+52`, `P`→`+56/+60`, and `M`→`+64/+68`. At `0x3200d889`–`0x3200d8a6`, ASCII `M` (77) selects its numeric field for `0x3201d170`; the returned words are stored at `+64/+68` as a binary64 value. At `0x3200d8e1`–`0x3200d902`, `M` is clamped to at least 5.0. The parser then checks `L` (76) and `C` (67): `L` writes 0 to context byte `+0`, while `C` writes 1. Thus `C` is parsed positionally, and the marker independently selects a mode.

The same parser stores `U`→context `+24/+28`, `D`→`+32/+36`, `Z`→`+40/+44`, `T`→`+48/+52`, `P`→`+56/+60`, and `M`→`+64/+68`. In dispatcher case 4 (`C2.306.5: 0x3200dd30`–`0x3200de31`), the fixed-slot value at `+72/+76` is converted to an integer before branching on the marker byte. L/zero mode stores the full integer in the ten-entry 32-bit history at `0x32007c00` and recomputes its mean at `0x32007c28`. C/nonzero mode stores the low byte in a separate ten-byte history rooted at `0x32007bc0`. It compares the new byte with the prior mean at offset `+10`: if new ≥ prior mean, it fills all ten history bytes with the new value so the mean becomes that value; otherwise it keeps the circular-history update and recomputes the floor-average at `0x32007bca`. The C history's update rule is therefore asymmetric, not just a second rolling average. Neither buffer's units or physical source are established by these operations.

Dispatcher case 5 (`0x3200d9e0`–`0x3200dbd6`) uses the marker differently. In C mode, the C-history mean is read only as the `%d` argument for the diagnostic string `radius[10]=%d,bright_h=%f bright_d=%f!`; it is not fed into the scheduler math. In L mode, the DSP reads the L-history mean at `0x32007c28`, converts it to binary64, divides by binary64 `1.2`, then adds that result to M at context `+64/+68`. The `[0x32028c7c]+40` source belongs to a different dispatcher case and is not the case-5 M operand. Shared case-5 code combines P and the resulting M, stores a derived value at `0x3200b954`, and submits callback `0x3200e01c` through queue helper `0x320149b0`.

The callback compares the queued value against `0x3200b8fc` when its status byte is set. Its branches can update the DSP state bytes to `(+3=0,+5=8)` or `(+3=1,+5=6)`; these numeric states have no recovered domain labels, so they should not be called a proven layer-complete or motion state. I found no direct RPMsg operation in this callback. Another worker path selects the numeric thresholds 20 or 200 based on the L/C marker (`0x3200dfe6`–`0x3200e016`), but their role is also unknown. C2.305.26 contains the same L/C history and callback graph with corresponding code blocks generally shifted by `0x20`, confirming static lineage across those two R6 releases only. These disassemblies bound the internal data flow; they do not establish physical units or effects, and no live R6 RPMsg trace is available.

At `0x3200d78e`, an L32R resolves to the `M678` string at `0x3200259c`; the subsequent call to `0x3201b5d0` is a verified substring-search helper and branches away if `M678` is absent. At `0x3200d7af`, the handler passes candidate buffer `0x32028f40` and the `P2` string at `0x320024c0` to that same helper. In this Xtensa `call8` path, the caller's `a10/a11` arguments become the helper's `a2/a3` after register-window rotation. If `P2` is present, the branch calls `0x32014704(139, 0)`; if absent, it calls `0x32014704(139, 0)` and then `0x32014704(140, 0)`. Both branches continue to the common parse wrapper at `0x3201d170`. The helper packages the index and selector `1` for dispatcher `0x320145c8`; static mapping in `0x320143d8` shows IDs 139 and 140 target bits 11 and 12 of the same backing word at offset `+80`. The P2-present branch clears bit 11, while the P2-absent branch clears bits 11 and 12. Neighboring M106 code writes the same pair: `S0` clears both, `S255` sets both, and a P2 branch maps ASCII `1` to clear and `0` to set the two fields from input bytes `[a2+21]` and `[a2+22]`. This ties the fields to parsed command state, but their device-level names and physical meaning remain unknown, and no live R6 RPMsg capture confirms end-to-end behavior. The CL-60 V1.89 STM32 independently checks exact token slot 8 for `P2` in its `M678` parser, but takes a separate bit-band-output branch; shared spelling does not establish the same action. The host's `+0x18c` byte independently gates whether R6 PrinterUI appends `P2`.

## Public protocol evidence and alternative firmware limits

The closest public HALOT-ONE reverse-engineering write-up is the 2022 Creation Factory article, based on an older 2.202 beta-era build. It independently describes TinaLinux/OpenWrt, root access, `PrinterUI`, the Wi-Fi file-transfer service, and logged CL60 movement strings such as `G0 Z170 F1 D1 S1 H2`; its author labels `D1` up and `D0` down, supporting `D` as a direction selector for that command. The log does not establish that this jog/manual-move command is the per-layer motion transaction: our later capture shows `M678`/`M114`, and the article does not document that layer-completion exchange. Its logs show CL89 and CL60 machine identifiers, aligning with the host-side multi-model design found here, but it predates the 2.238.2 and 2.303.1 binaries compared here. A 2023 HALOT-MAGE owner discussion reports that an attempted serial connection produced no input or output; replies point to unidentified board pins, but no electrical trace or protocol follows. It is weak negative evidence only: the post does not show which interface was tested or prove that the printer lacks a UART control path. Searches for `M678`, `M410_OK1`, `M114`, UART traces, and logic-analyzer captures across the public materials checked for SKY, ONE PLUS, MAGE, and LD-series machines did not locate an independent STM32 command table or wire trace. That is a bounded search result, not proof that no such material exists.

As of the 2026-09-30 source check, no public complete replacement firmware or printer backend explicitly targeting the HALOT-ONE CL-60 was found. Keep the projects below separated by what they replace or extend:

- **Printer/controller firmware:** Turbo Resin's documented targets are Anycubic Mono 4K and Saturn; its README lists Creality among desired future printer families. The Mage S and Mage Pro releases modify those models' vendor firmware images to add root/SSH or file transfer; they are model-specific overlays, not a new motion-control stack. Neither provides a CL-60 image or board target.
- **Host-side printer control:** Mariner and OctoPrint-Chituboard target ChiTu-based LD-002H/LD-002R systems. NanoDLP is a host print manager that PrometheusOS maintainers characterize as non-open-source; its documented Marlin firmware is a separate component for NanoDLP's own controller board. Odyssey is designed for Apollo/Prometheus and uses configurable serial/G-code/display abstractions. Creality-Control is a Home Assistant network integration for monitoring and active-job controls, not a print backend. Its README claims an unnamed Halot test, but the model-specific tracker still marks Halot models as needing tests and its Halot-One test link opens a report-creation form; that generic claim does not establish CL-60 support.
- **UI, slicer, and job-format plugins:** Orion's current README documents a UI for Odyssey; GitHub's repository description advertises Odyssey and NanoDLP, but the inspected source does not verify NanoDLP compatibility. DragonFruit is a desktop slicer with a separate plugin ecosystem, not printer firmware. The current ORA catalog lists CTB, SDCP V3, Anycubic, Elegoo, Siraya Tech material profiles, LYS import, ChiTuBox import, and UniFormation; it lists no Creality/HALOT plugin. VoxelShift converts resin job formats for NanoDLP, and LUMEN is an open job format. These can inform file, profile, or UI adapters, but they do not implement the CL-60 STM32 contract or display path.

At the 2026-09-30 recheck, Creality's HALOT-ONE product download page still rendered `firmwareList:[]`; its firmware card showed `Sep 29, 2026` but had no version/title or populated download URL. The page component selects the first firmware-list item, and the shared card formats its `releaseTime` even when that item is absent, so this date is a UI fallback rather than evidence of a release. The newest identified downloadable HALOT-ONE archive remains the 2023-09-21 `2.303.1` package listed in the owner's Creality Cloud screenshot.

Creality's Dec 2025 official open-source announcement links three Klipper projects: K2 Plus, Creality Hi, and K1 Series, and says additional models may follow. The checked repository heads on 2026-09-30 were [K2 `bc0a52078ace1e4d82995e396b38457b9f441024`](https://github.com/CrealityOfficial/K2_Series_Klipper/commit/bc0a52078ace1e4d82995e396b38457b9f441024) (release [`V1.1.3.13`](https://github.com/CrealityOfficial/K2_Series_Klipper/releases/tag/V1.1.3.13)), [Hi `646b6aaaa4dc1fe9c4f773f1a425ea4666e5ed9b`](https://github.com/CrealityOfficial/Hi_Klipper/commit/646b6aaaa4dc1fe9c4f773f1a425ea4666e5ed9b) (release [`V1.1.0.50`](https://github.com/CrealityOfficial/Hi_Klipper/releases/tag/V1.1.0.50)), and [K1 `e09f36e6ada60e5467b0bef731a96263b5d8095b`](https://github.com/CrealityOfficial/K1_Series_Klipper/commit/e09f36e6ada60e5467b0bef731a96263b5d8095b) (release [`V1.3.3.5`](https://github.com/CrealityOfficial/K1_Series_Klipper/releases/tag/V1.3.3.5)). Their READMEs identify their respective FDM families and the trees contain Klipper source/configuration alongside target-specific firmware blobs. A two-page snapshot of the 119 public repositories listed by the [`CrealityOfficial` organization API](https://api.github.com/orgs/CrealityOfficial/repos?type=public&per_page=100&page=1) contained no repository name or description with `HALOT` or `resin`; [page 2](https://api.github.com/orgs/CrealityOfficial/repos?type=public&per_page=100&page=2) held the remainder. These sources are useful for comparing Creality's Klipper changes and update packaging, but do not provide a resin exposure pipeline, CL-60 board target, or evidence of a shared resin STM32 protocol. The repository survey is bounded to that public organization and snapshot; it does not rule out internal code reuse or another publication.

The Mage S/Pro nearest-stock comparisons are summarized below; version skew prevents assigning all payload differences solely to the community modifications.

The current public evidence separates into three levels of reuse. **Reusable host-side structure:** Odyssey's [`PrintFile`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/printfile.rs), [`HardwareControl`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/printer.rs), display abstraction, and API endpoints provide places for a HALOT job reader, layer scheduler, status reporting, and operator controls. At the current upstream `main` commit [`f7c8e685`](https://github.com/Open-Resin-Alliance/Odyssey/commit/f7c8e68537848eabf3be09841a924d42b9a82403), `PrintDisplay` packs configurable pixel groups with left/right padding and optional byte-order inversion. The bundled Athena2 configuration uses eight 3-bit samples plus 8 right-pad bits per 32-bit group. This is a useful generic packing reference, but not the CL-60 transform: stock HALOT groups three 8-bit source samples into `[sample[2], sample[1], sample[0], 0xff]` for a 540×2560 BGRA HDMI input, then uses the H616 HDMI → RK628 → MIPI path. Odyssey writes its re-encoded bytes to a Linux framebuffer. The packing code may inform a HALOT serializer, but its Athena2 layout and framebuffer sink do not provide the CL-60 display driver. Odyssey's documented target remains Apollo/Prometheus, and its stock print cycle does not encode the captured CL-60 `image → M678 → M114` sequence. **Reusable job data:** the [LUMEN Rust reader](https://github.com/Open-Resin-Alliance/LumenFormat/tree/main/rust) is a candidate input adapter for layer masks and metadata; it is a format reader, not a printer transport or panel driver. **Useful comparison only:** [Turbo Resin](https://github.com/nviennot/turbo-resin) is a Rust embedded firmware whose checked-in board targets are Mono 4K and Saturn, and whose documented flash path uses SWD probes. Its embedded patterns may inform independent-controller work, but its board drivers and firmware image are not CL-60 compatible. Likewise, the [Creality-Control compatibility tracker](https://github.com/SiloCityLabs/Creality-Control/issues/1) classifies HALOT as a separate protocol and still requests model tests; its Halot Box-derived WebSocket controls are evidence for the network/UI layer only. None of these sources provides the missing CL-60 panel sink, STM32 electrical contract, or command semantics.

### What ORA code can be reused for a HALOT backend

Odyssey provides useful extension points, but its current layer loop does not match the captured CL-60 cycle. Its `HardwareControl` trait exposes high-level readiness, homing, Z motion, UV, and shutdown actions, while its `PrintFile` trait is the natural place to add a job reader. The inspected `main` registers only `.sl1`; its reader extracts PNG layers from a ZIP. Its HTTP upload/start/pause/cancel/status endpoints could be retained for a HALOT service. See [Odyssey `printer.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/printer.rs), [`printfile.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/printfile.rs), and [`api/print.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/api/print.rs).

The current Odyssey `print_frame` sequence raises/lowers Z, waits, sends an image, toggles UV with timers, and then waits again. The CL-60 host instead submits the exposure image, sends an `M678` layer command, and polls `M114` before advancing. A HALOT implementation therefore needs a changed layer scheduler and a serial transport/parser for the fixed-frame UART contract; a G-code template alone cannot express that exchange cleanly. Odyssey's current `PrintDisplay` writes to a Linux framebuffer, but the CL-60 exposure path uses H616 HDMI → RK628 → DSI, while `/dev/fb0` is the operator display. The image sink must target the HALOT display API, not just the regular framebuffer. See Odyssey [`display.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/display.rs) and [`gcode.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/main/src/gcode.rs).

LumenFormat's Rust reader is a candidate input adapter, but its current `LumenFile::open` borrows the complete container as `&[u8]`; it decodes a layer's compressed frame on request. The API exposes `layer()` for sector 0, `layer_sectors()` for all nonempty masks on a layer, and `timing_for(layer, sector)` for the sector's resolved metadata, bottom/transition blending, and `LROV` override. LUMEN sectors are separate cure-and-move cycles in ascending sector order. A first CL-60 reader must therefore detect and reject multi-sector jobs unless the backend implements those extra cycles; silently using `layer()` would omit data. It must also apply `LROV` or reject jobs that use it. The reference crate requires Rust 1.85 and is dual-licensed MIT OR Apache-2.0. HALOT still needs its own mask conversion, CXDLP/LUMEN job integration, layer scheduler, and display sink.

There are two source/documentation mismatches to resolve before treating the ORA chain as plug-and-play. First, the current LumenFormat README says DragonFruit imports the repository root as `plugins/lumen`, but the inspected DragonFruit `main` commit `f6c7a20043c16c54d6263c6bb7e308a5f6d27377` has no Lumen submodule in `.gitmodules` and no Lumen entry in either plugin allowlist. LumenFormat contains the plugin source; this finding is about its integration into that DragonFruit snapshot, not about adapter availability. Second, the current LumenFormat README says Odyssey consumes LUMEN through Orion and implements its `PrintFile` trait over `LumenFile`, while the inspected Odyssey `main` commit `f7c8e68537848eabf3be09841a924d42b9a82403` has Odyssey version 0.4.1, no LUMEN crate dependency in `Cargo.toml`, and `src/printfile.rs` registers only `.sl1`. The `main` heads were rechecked on 2026-09-30: DragonFruit `f6c7a20043c16c54d6263c6bb7e308a5f6d27377`, Odyssey `f7c8e68537848eabf3be09841a924d42b9a82403`, LumenFormat `109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda`, and Orion `65bba7a87c8547e5e8fe3aec58b0adeaa2b087d9`. These checked source snapshots do not corroborate an out-of-the-box LUMEN → DragonFruit → Orion/Odyssey workflow, although LumenFormat's documentation claims that integration. This does not rule out manual integration or changes after the pinned commits. See [LumenFormat README at the checked revision](https://github.com/Open-Resin-Alliance/LumenFormat/blob/109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda/README.md), [Rust reader](https://github.com/Open-Resin-Alliance/LumenFormat/blob/109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda/rust/lumen/src/reader.rs), [crate manifest](https://github.com/Open-Resin-Alliance/LumenFormat/blob/109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda/rust/lumen/Cargo.toml), [sector model](https://github.com/Open-Resin-Alliance/LumenFormat/blob/109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda/spec/13-sectors.md), [per-layer timing](https://github.com/Open-Resin-Alliance/LumenFormat/blob/109d7d444c9714d8d41f3e3e0ddb47e21eaa1eda/spec/14-layer-timing.md), [DragonFruit `.gitmodules`](https://github.com/Open-Resin-Alliance/DragonFruit/blob/f6c7a20043c16c54d6263c6bb7e308a5f6d27377/.gitmodules), [DragonFruit simple-plugin allowlist](https://github.com/Open-Resin-Alliance/DragonFruit/blob/f6c7a20043c16c54d6263c6bb7e308a5f6d27377/src/config/builtin-simple-plugin-allowlist.json), [DragonFruit complex-plugin allowlist](https://github.com/Open-Resin-Alliance/DragonFruit/blob/f6c7a20043c16c54d6263c6bb7e308a5f6d27377/src/config/complex-plugin-allowlist.json), [Odyssey `Cargo.toml`](https://github.com/Open-Resin-Alliance/Odyssey/blob/f7c8e68537848eabf3be09841a924d42b9a82403/Cargo.toml), [`printfile.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/f7c8e68537848eabf3be09841a924d42b9a82403/src/printfile.rs), and [`display.rs`](https://github.com/Open-Resin-Alliance/Odyssey/blob/f7c8e68537848eabf3be09841a924d42b9a82403/src/display.rs).

Orion can be a separate UI if the HALOT service implements its expected Odyssey API; its inspected [`ApiService`](https://github.com/Open-Resin-Alliance/Orion/blob/main/lib/api_services/api_services.dart) is Odyssey-shaped. VoxelShift demonstrates a CTB-to-NanoDLP plate writer and upload/start client, but its `.nanodlp` output is not a file type the inspected Odyssey source currently accepts. NanoDLP's configurable command fields and board parser offer another host route, but no reviewed code or docs supplies the CL-60 `M678`/`M114` contract or RK628 sink. In short, LUMEN/CTB readers, a UI, and upload APIs are reusable pieces; the HALOT scheduler, UART driver, and exposure sink are the core new backend work.

The Mage Pro project also documents reverse engineering of its embedded `Dwarf` slicer/firmware application and work on print-parameter acceptance. That is useful evidence that other HALOT models have active community modification work, but it is not a STM32 protocol trace and does not provide a CL60 port. The Mage S Toolkit tray client uploads over the printer's FTP service into `media/mmcblk0p3`, then sends a WebSocket `START_PRINT` request with a token and filename; it also polls `GET_PRINT_STATUS` and uses token-bearing `PRINT_PAUSE`/`PRINT_STOP` messages ([client source](https://github.com/rogersstuart/Halot-Mage-S-Toolkit/blob/main/ftp_serv.py)). This is a client of the Mage S vendor service, not replacement printer firmware. Static analysis of CL-60's recovered `libcxWebsocket.so` confirms that its non-secure WebSocket service also uses the `cmd`-based `START_PRINT`, `GET_PRINT_STATUS`, `PRINT_PAUSE`, and `PRINT_STOP` vocabulary. The CL-60 upload path is different: it begins with a `START_FILE` JSON request and then sends binary WebSocket messages acknowledged with `START_DATA`/`CHECK_DATA`, rather than the Mage S client's FTP transfer. The CL-60 status reply shares `printStatus`, `filename`, `printRemainTime`, `curSliceLayer`, and `sliceLayerCount` with Creality-Control; `progress` is absent. A read-only authenticated status exchange with the live printer confirmed this schema. Only `GET_PRINT_STATUS` has been exercised against the live CL-60 WebSocket service; start, upload, pause, and stop remain untested through that interface. Static analysis traces pause to `M410 S0`/`M114` polling and one stop branch to `M410 S2`/`M114` plus a runtime-built move, while the passive print trace independently records manual UI pause traffic. These paths still do not confirm physical actuator behavior. The shared command words therefore suggest application-layer lineage, while job-transfer transport and actuator behavior remain model-specific or unverified. See [the detailed CL-60 WebSocket protocol map](network-control-protocol.md).

The R6 display also differs from CL-60 despite a matching nominal panel resolution. Creality's parts listings identify an R6 6.08-inch 1620×2560 exposure screen, a separate 240×320 touch display, and an `R528 MIPI` mainboard. Its R004 ini profile sends images as `FB`; CL-60's profile sends 540×2560 BGRA through `HDMI`, and our physical/software trace reaches the panel through HDMI→RK628→MIPI. Resolution alone therefore does not establish matching pixel format, timings, bridge, or panel wiring. For the original HALOT-SKY, the teardown reports H6 + STM32F103 + LT6911C HDMI-to-MIPI, which is the closest public architectural analogue to CL-60 but still a different SoC and bridge. Public MAGE materials establish panel size/resolution and board SKU but not the complete host-to-panel signal chain.

This contrasts with CL-60, whose rootfs contains a standalone `V1-01.bin` and `mcu_tool` startup updater for `/dev/ttyS2`; it does not prove that Mage Pro has no MCU-related code embedded inside a filesystem.

The Mage Pro mod's README advertises root/SSH and file-transfer changes. Its NAND/UBI container is a different update route from the CL-60 Allwinner/eMMC SWUpdate package, and its released image is not compatible with CL-60.

This update format differs from both the CL-60 SWUpdate/eMMC package and the MAGE S/PRO `ChituUpgrade.bin`/NAND/UBI packages; none is a safe cross-model firmware image.

## Shared layers versus non-shared contracts

The ecosystem has at least four contracts, and evidence for one cannot stand in for another:

1. **Job container:** CXDLP/CXDLPV4, layer masks, thumbnails, and print metadata.
2. **Linux-to-controller control:** fixed UART frame and command/reply dialect on `/dev/ttyS2` for this CL-60.
3. **Image presentation:** the separate H616 HDMI → RK628 → MIPI DSI path and the panel's pixel/channel mapping.
4. **Electrical board interface:** connectors, signal levels, motor driver, UV outputs, sensors, and boot/reset wiring.

Public CXDLP support establishes layer 1 only. Our live trace and static disassembly establish much of layer 2 for one firmware. The H616/RK628 trace establishes a large part of layer 3, but physical pixel mapping remains open. Layer 4 still needs board-level evidence. A model can share CXDLP while differing in every other layer.

## Port implications

There are two different reuse candidates, for different purposes. The closest **device-software lineage** is Creality's older HALOT host/controller family: a shared official 2.238.2 image set across four model entries, multi-model `PrinterUI` profiles, matching host layer builders, the normalized instruction-identical M678 worker/TIM3 core across V1.821 and V1.89, and closely matching sampled command handlers. The best **open-source host architecture** to study is Odyssey, but its Apollo/Prometheus deployment targets different hardware and does not contain the HALOT wire protocol or panel driver.

A local Odyssey working branch now has an inert `halot-inspect` planning path that joins a decoded CXDLP layer with a candidate BGRA buffer and an `M678` string; unresolved runtime tokens remain explicit inputs, and an optional schedule file can vary them by layer. The command is only printed or written to a local sidecar. This is useful for reviewing the host-side layer contract, but it is not connected to Odyssey's active print loop or hardware. A real CL-60 backend must adapt the serial framing, per-layer scheduler, and display submission while retaining the existing board-specific paths. The evidence does not justify flashing another model's complete image or calling its MCU behavior verified on CL-60.

The Mage S/Pro rooted updates modify their vendor Linux images and use a Chitu/NAND/UBI update path that cannot be transplanted to CL-60's Allwinner/eMMC SWUpdate layout. Odyssey and NanoDLP are host-side architecture references that need adapters for CL-60's fixed UART frames, image submission route, and completion replies. DragonFruit's plugin architecture is a possible slicer/job-format contribution point, not a device-control implementation. A full from-scratch controller replacement has a much larger unknown surface: board pinout and voltage levels, motor and sensor IO, UV control, boot/debug access, and the panel data path are all separate work items.

## What to investigate next

The current official download cards surfaced for Mage S and Mage Pro are `.06` and `.04`, while their older-version records include Mage S `.311.04`/`.308.07` and Mage Pro `.309.03`/`.304.10`; the two Mage S catalog links are crossed but their inner updater headers resolve to the expected releases. The exact clean Mage S `.07` and Mage Pro `.09` stock counterparts remain unlocated. Searches found only owner reports for Mage S `.07` (their posts have no firmware attachment) and a modified Mage Pro `.9` image. Search historical CDN/API records or independently archived clean packages to separate version changes from each community overlay. Other open work is to trace the source of the effective CL-60 `Z/U/D` values that differ from XML defaults; establish the physical meaning and units of the R6 `C` value, its L/C marker modes, M, P, and the thresholds 20/200; identify the physical effect of the queued DSP callback and the domain labels for its numeric state bytes and bits 11/12; explain why CL-60 layer zero sends the panel-geometry `L` value and what physical quantity the STM32's filtered-area thresholds represent; and explain when R6's `+0x18c` flag causes `P2` to be appended and how that relates to the distinct CL-60 STM32 branch. This workspace contains no R6 CXDLPv4 job fixture or runtime RPMsg capture. Also capture passive UART traffic from a sibling machine to test the shared-protocol hypothesis, compare the Mage S WebSocket/FTP client against CL-60 network traffic, and map the R6/RK628/panel pixel path beyond matching nominal resolution. Any future binary match should be reported by cryptographic hash; similar filenames or shared command names are insufficient.

Do not send motion, reset, or UV commands to the CL-60 just to check whether another model's protocol is accepted.
